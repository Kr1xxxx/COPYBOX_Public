# Backup import limits and 允许 for 秘密 over the command line

- Date: 2026-10-14 · Thread/agent: 安全 · 本機加密、Mac 自動化介面、備份匯入加固 (audit items A4, A6, A8)
- What changed: Backup files (full backup, 话术/秘密 backups, old device backups) are refused when they name a PBKDF2 count outside 100 000…5 000 000, or carry a malformed salt / IV (`app/pbkdf2-limits.ts`, `app/data-transfer.ts`, `app/page.tsx` importVault); every key derivation (`app/key-cache.ts`, `app/account-lock.ts`) also caps the count, so a tampered record restored from a backup cannot freeze the app. On the Mac command line, `secret-get`, `secret-verify` and `secret-export` now wait for 允许 in the app (`app/automation-consent.tsx`, dialog in `app/dialogs.tsx`; refused after 45 s, one question at a time) and are refused while the 账号 page is locked; the shell brings the window forward and waits 60 s for these (`src-tauri/src/automation.rs`). `docs/HANDOFF.md` brought up to 2026-10-14 (coordinator's request).
- User-visible change (plain Chinese, for the preview changelog): Mac 命令行读取或导出秘密时，Copyboxx 会先弹窗问「允许读取秘密吗？」，点「允许」才给；账号页上锁时直接拒绝；导入备份时会拒绝被改坏的文件，不会卡死
- Not done / risks: The device key still sits next to the data (D-015); moving it to the OS credential store waits for the owner. A per-start token on the socket was not added: any program that can reach the socket can also read a token file as the same user, so the in-app question is the real gate. The 允许 dialog has not been seen on a real Mac (D-014).
- Next step: Device key in Windows Credential Manager once the owner picks an option (new D-number superseding D-015, high-risk PR).
